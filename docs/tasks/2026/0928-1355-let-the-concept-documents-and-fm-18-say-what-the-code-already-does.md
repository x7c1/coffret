# docs: let the concept documents and FM-18 say what the code already does

## Overview

Eleven places where a concept document or the format spec says less than, or other than, what the code and the rest of the spec already do. Every change is to prose under `docs/`, plus one doc comment; nothing changes behaviour.

1. **FM-18 permits renaming the app folder, but nothing can find a renamed one.** FM-18's last sub-bullet (`docs/spec/format/README.md`, around lines 522-526) says a user may name the app folder something else and coffret then reaches the Library at the name it is configured with. The folder's name is the only place a Library ID lives outside a configured device: `join` reads the ID from it (`coffret-device/src/join_library/run.rs`, `library_of_folder_name`), and discovery from a Recovery Code enumerates `coffret-*` names. A renamed folder can therefore never be joined by a new device. On Drive a device already configured keeps reaching it, because it holds the folder's Drive ID, but that is a consequence of how the Drive adapter addresses a folder, not a promise; on S3 there is no rename, only moving every object to another prefix, which no configured device follows. Replace the permission with the rule: the app folder's name is how a Library is found, and a user does not rename it; a renamed folder is not found by `join` or by discovery, and how an already configured device behaves is not specified. Do not describe a way back — the ID a renamed folder lost is held only by devices already configured, and a refused device cannot tell which Library a folder was. Keep the sub-bullet's form note (prose, not a test). `NotALibraryFolder`'s sentence does not change.
2. **FM-18 cites RV-1 where RV-2 is the nearer rule.** The sub-bullet on finding the folder from a Recovery Code (around line 517) cites "(KL-1, RV-1)" for keeping the folder whose Keyring authenticates under the code's Master Key. Read RV-1 and RV-2 in `docs/spec/recovery/README.md` and cite the one that states it (add RV-2, or replace RV-1 with it); do the same in `docs/concepts/recovery-code/README.md` (around lines 51-52) where it repeats the claim.
3. **The Keyring concept uses *element* without defining it.** `docs/concepts/keyring/README.md` says the set digest changes "if any element of the mapping changes" (around line 36) and the code centres on `KeyringElement`, but the concept never says what an element is. After the State section's key-status paragraph (around lines 44-47), add one sentence: each element of the mapping names one current Container and its key status.
4. **KL-16 is half-stated in the Keyring concept's Mental Model.** The Mental Model (around line 80) says that when a repair cannot complete, "reads go on"; the Domain Rules (around line 145) and the spec (`docs/spec/keyring-lifecycle/README.md`, around line 85) say reads *and restores* go on. Say "reads and restores go on" there, and in the doc comment that repeats it (`coffret-usecase/src/commit/commit_error.rs`, around line 101).
5. **The Library concept's finding rules lack the Container-level key-lost finding.** The device already reports a Container whose key the Library records as lost (`coffret-device/src/finding.rs`, around lines 85-93, `Finding::LockedContainer`), but the finding rules in `docs/concepts/library/README.md` (around lines 297-311) do not list it. Add a sub-bullet for it, citing KL-7, KL-17 and RV-7.
6. **The Library concept does not point to the rule that keeps names inside a Library out of diagnostic events.** It cites EL-1 for the device-local Library name only (around lines 17-19); the rule that Entry Paths and file names stay out of diagnostic events lives in the Entry Path concept's Domain Rules (`docs/concepts/entry-path/README.md`, around lines 71-75). Add a sentence with a link there.

7. **The verb for clearing a refusal is used everywhere but registered nowhere.** EP-14 says a refusal is *remedied* (`docs/spec/entry-path/README.md`, around lines 317-321), and the code uses *remedy* for the gesture that clears a refusal or a state a run keeps reporting, keeping *resolve* for path resolution. The Library concept's Collocations register *refuse* and *surface* but not the verb that answers them. Add one entry, for example "remedy (a refusal, or a state a run keeps reporting, by the gesture its report names — renaming a folder, naming a different Entry Path, recording a mapping afresh)".

8. **The Library and Index concepts do not cover what a run now reports about its commit and a refused disposal.** The device reports an untrashed removal and a checkpoint not written as findings of the settled kind (said, not escalated), and a disposal Storage refused as an object left in Storage for orphan cleanup to find. In `docs/concepts/library/README.md`, the finding rules call settled "the one kind nobody has to act on" — make it the kinds, and add a sub-bullet for what a commit could not finish after its record (spec: OC-6, CK-8); under the settle rule, add that an uploaded object Storage refuses to trash stays while its row goes, becoming a suspected orphan retained for orphan cleanup and a person (spec: OC-1, OC-4). In `docs/concepts/index/README.md`, the *dispose* collocation should say that disposing of the object does not happen when Storage refuses, while the spool and the row are still disposed of.

9. **EP-1's list of text arriving from outside does not name the explorer's URL.** The explorer now normalises the folder and file a URL hash names to NFC as it parses them. EP-1's sub-bullets (`docs/spec/entry-path/README.md`) and the Entry Path concept's Domain Rule ("Text arriving from outside — a name read off a disk, a component a mapping is configured with, a prefix a caller narrows a run to —", `docs/concepts/entry-path/README.md`) should list it too; say that the hash is normalised and never refused (an unreadable one reads as the Library root), unlike `?path=` which EP-2 refuses where it arrives, because the hash is the browser's own view state and not an input to the server.

10. **No concept says what a folder standing on disk with no Entry under it is.** The explorer's listing now names such child folders (`folders_on_disk`) so a new folder is never made over them. Under the Library concept's *added* Domain Rule (`docs/concepts/library/README.md`), add a sub-bullet: a folder standing in a mapped folder with no Entry under it is not a folder of the Library (spec: EP-2); a listing names it rather than drawing it, so that a new folder is never made over files already there.

11. **The Keyring concept does not tell *short* from *degraded*, and the Library's finding rule misses the degraded-Keyring finding.** The code now reports a read that only failed to fetch a replica as "not established" rather than degraded, and a run that read through a stepped-over position without reaching an examination reports it as a finding nobody has to act on, repeated by later runs until a writer repairs the set. In `docs/concepts/keyring/README.md`, after the health-event paragraph ("A run that found the set short and reached no commit at all …"), add that where every position stepped over was one Storage would not hand over, nothing is known to be lost, and the run says so rather than calling the set degraded (spec: KL-15); state the distinction — *short* is a set missing a valid replica at some position, fetch failures included; *degraded* is a loss established (KL-5). In `docs/concepts/library/README.md`, extend item 8's finding sub-bullet to name this finding too (spec: KL-15, RV-2). In the Keyring concept's health-event paragraph, say that a run of any kind — sync, freeze, or the explorer's fill — reports it among its findings, so the code's `findings` and the concept's health event are visibly one thing. And where it says "a run that commits reports every position it put back" (around lines 86-88), say that a run reports every position it put back whether it commits or fails after the repair (spec: KL-15).

Review found that item 11's distinction reached further than the concept documents, and this change follows it there. `CommitError::UnrepairedKeyring` and `UnrepairedReplica` said *degraded* of a set whose only unrepaired positions may be ones Storage would not hand over; they now say *short*, and so does the `warn!` line the refusal writes (`coffret-usecase/src/commit/keyring.rs`) — a log sentence, read by no test and by no wire contract. KL-15 gains the sub-bullet the code and the concept already cited it for: a run reports as loss only what a read established. `Finding::DegradedKeyring` and the `keyring_degraded` reason keep their names: the finding answers whether the set is degraded and carries whether that is established. And `join_library/run.rs`, which said FM-18 leaves renaming to the user, says FM-18 tells them not to.
